# forms extension

A drag-and-drop **contact-form builder** plus the `[contact-form]` shortcode/element to place forms on any page. **How you get it:** not in the core-only plugin zip — download + activate it from **Unyson+ → Extensions** (it pulls in `builder`; its Contact Forms sub-extension requires `mailer`).

## Provides

- **Shortcodes:** `[contact-form]` — the form element (also a page-builder item) → see `../shortcodes/`.
- **Option type:** `form-builder` (`includes/option-types/form-builder/`) — the drag-and-drop field builder used to compose a form.
- **Sub-extension:** `contact-forms` (`extensions/contact-forms/`) holds the shortcode + item.
- **Settings/options:** a `settings-options.php` page (spam / reCAPTCHA / default recipient etc.); per-form config lives in the form-builder option on each form.
- **Public hooks/filters:** standard forms hooks (see `hooks.php`) — submission handling, validation, and mail dispatch.
- **Entries (since 2.0.50):** every submission is stored in `{prefix}fw_form_entries` and listed under **Unyson+ → Form Entries** — per-form filter, status views (New / Read / Archived), date window, search (including field values), bulk archive/delete, single-entry view, CSV export of the current view. Settings: `entries_store` (default on), `entries_store_ip` (default off), `entries_retention_days` (0 = keep). Registered with the WordPress Export / Erase Personal Data tools by email.
- **Field types (since 2.0.51):** `date` (native date / time / datetime-local input; `min`/`max` accept ISO or `today`; blackout weekdays; server-validated), `rating` (radio group styled as 1–5 stars or 0–10 / 1–10 pills; integer value; optional end labels), `hidden` (static value, URL parameter, page URL or page title — context, never authority), `consent` (dedicated type with `purpose` = terms / newsletter / other; a newsletter opt-in is forced optional; unticked stored as `''`). `FW_Option_Type_Form_Builder_Item_Consent::newsletter_consent_given( $fields )` is the one test for a newsletter opt-in. The four share `_shared/class-fw-option-type-form-builder-item-simple.php` + `_shared/js/simple-item.js`.
- **Actions (since 2.0.52):** per-form on-submit steps on a **Settings → Actions** tab of the contact-form element, registered via `fw_ext_forms_actions` (`FW_Forms_Action`: id / title / options / run). Forms ships **Store entry** (`action_store`, default on); the CRM adds **Add to the CRM** (`action_subscribe` + `action_subscribe_list` / `_tags` / `_name`, default off, consent-gated). Exact atts in `../shortcodes/contact-form.md`. Runner at priority 20 on the submit hook, after entry capture; failures reported via `fw_ext_forms_action_failed`, never shown to the visitor. `fw_ext_forms_form_settings` is how a form type hands its saved atts to actions.
- **Front-end assets load on demand (since 2.0.55):** `fw-ext-forms-default-styles` + `fw-ext-forms-conditions` are only *registered* globally; `FW_Extension_Forms::enqueue_frontend_static()` enqueues them, called from the contact-form shortcode's `static.php` (so they print in `<head>` on pages with a form) and from `render_form()` as a footer fallback for forms rendered any other way. A new form type that renders outside `render_form()` must call it. The builder grid (`fw-ext-builder-frontend-grid`) is still enqueued globally by `forms/static.php` — the theme layout depends on it.
- **Conditional visibility (since 2.0.53):** every field has a *Show only when…* rule (controller field by label · is / is not / contains / has any value / is empty · value). Toggled live by `static/js/conditions.js` from rules the form emits as JSON, and **enforced server-side**: a hidden field is neither validated nor collected. An unresolvable rule shows the field rather than hiding it.
- **Starter forms (since 2.0.54):** the form builder has the framework's Templates panel (`template_saving`), with the starters (fifteen since 2.0.69) via `fw_ext_builder:predefined_templates:form-builder:full` (template ids `fw-forms-<id>`) — Contact, **Appointment request** (clinics / salons / professional services: name, email, phone, service, preferred date + time, first visit?; deliberately no free-text box, so it does not invite health or confidential details), **Table booking (restaurant)** (formerly "Booking"), Quote request, Event registration, Support ticket, Feedback (CSAT), NPS survey, Newsletter signup. Field-by-field list in `../shortcodes/contact-form.md`. Authored as PHP and normalised through each item class; a newsletter opt-in is always a separate optional Consent box, and no starter sets Actions. Extend with `fw_ext_forms_starters`.
- **Form Styles presets (since 2.0.67):** Theme Settings → Components → **Form Styles** (`form_style_presets`), added by this extension through `unysonplus_components_settings_options`; each preset is a `.formp-{slug}` class written into the shared presets CSS via `unysonplus_global_css`. The Contact Form picks one with `form_style` (default: the first preset, Standard, which reproduces the plain field look exactly); its own field settings are this-form-only overrides that win. Class `FW_Forms_Style_Presets` (`includes/styles/`): `all()`, `choices()`, `default_choice()`, `is_valid()`, `css()`; filters `unysonplus_default_form_style_presets`, `unysonplus_form_style_presets`. Full shape: `../theme-settings/form-styles.md`.
- **Sending (since 2.0.68):** forms post in the background (`static/js/submit.js`, handle `fw-ext-forms-submit`, enqueued with the other front-end assets) using FW_Form's built-in JSON reply, and fall back to the normal reload on any unexpected reply. Errors are inline + linked (`aria-describedby`), fields `aria-invalid`, a focused summary (`.fw-form-error-summary`) for several problems; the server's `ul.fw-form-errors` after a reload is converted to the same pattern. Contact Form: `confirmation_type` (message / hide / page / url), `confirmation_page`, `confirmation_url`, `email_cc`, `email_bcc`; an empty `email_to` uses the admin email. **Answer tags** `{shortcode}`, `{all_fields}`, `{site_name}`, `{page_title}`, `{page_url}`, `{date}` in the subject, success message and address (`FW_Forms_Merge_Tags::replace( $text, $values, $items, 'text'|'html'|'url', $post_id )`, filter `fw_ext_forms_merge_tags`). A field's **Field Name** (`options.tag`, since 2.0.89) is an alias: `{your_name}` and `{text_3f2a9c1}` both resolve (`FW_Forms_Merge_Tags::tag_of()`). The builder script (`form-builder/static/js/helpers.js`) moves the Field Name row under Label, fills it from the label, keeps it unique, strips braces, rewrites `{old}` → `{new}` in the form's own settings on rename, and adds a clickable tag list under every setting whose description mentions answer tags. **Autofill hints**: email → `autocomplete="email"`; text fields by label (`FW_Forms_Autocomplete::for_label()`, filter `fw_ext_forms_autocomplete_hint`).
- **Email the sender action (2.0.68):** `action_autoresponder` (off), `_subject`, `_message`, `_answers` (off). Sends to the primary email; replies go to the form's first recipient. Without `_answers` only name fields fill its tags (≤40 chars, links stripped), so a form cannot relay a stranger's text.
- **Human checks (2.0.68):** field types `turnstile` and `hcaptcha` (keys in Forms settings `turnstile-keys` / `hcaptcha-keys` `{ site-key, secret-key }`); explicit render (`_shared/js/captcha.js`), reset after a failed attempt; a field without keys renders nothing and never blocks; verification server-side.
- **Spam filtering (2.0.68):** Forms settings `spam_akismet` (needs the Akismet plugin with a key), `spam_blocked_words`, `spam_blocked_domains` (one per line), `spam_max_links`. A caught submission: normal success message, no email, no actions, entry status `spam` with a reason row (excluded from "All"; bulk Mark as spam / Not spam). `FW_Forms_Spam_Filter::is_spam( $form_id )`, filter `fw_ext_forms_spam_check( $reason, $fields )`.
- **Form-type picker (since 2.0.69):** an empty form builder (only the header item) opens on a grid of the starters, grouped, plus Blank; picking one fills the builder (`rootItems.reset` + `builder:change`) and the subject / button / thank-you text where still default. "Choose a form type" in the builder header reopens it. With an AI provider connected (WordPress AI Client), a box builds a form from a description (`FW_Forms_AI_Generate`, AJAX `fw_forms_ai_generate`, nonce `fw_forms_ai_generate`, `edit_posts`); the reply is validated per field and normalised like a starter; actions are never set. Starters now: contact, quote, callback, product, support, appointment, booking, registration, rsvp, job, volunteer, feedback, nps, signup, download — each with `desc`, `icon`, `group`, `settings` (filter `fw_ext_forms_starters`).
- **Form library (since 2.0.70):** Unyson+ → **Forms** lists saved forms (post type `fw_form`, private). Each is edited with the contact form's Form Fields + Settings tabs (post options) and shown by any Contact Form element via `library_form` (post ID); the element keeps Style/Advanced, submits as form id `lib-<ID>`, and its entries are titled with the form's name. List columns: fields, entries, placed on; row actions Duplicate and Export (JSON `{ type: 'unysonplus-form', title, version, fields, settings }`); Import above the list. Revisions: the definition is mirrored into post_content, and restoring a revision restores the form. `FW_Forms_Library::definition( $id )`, `create( $title, $data )`, `import_into()`, `export_shape()`, `placements()`, `choices()`. In the page builder: saved forms appear in the picker, a linked element shows a notice instead of its own fields, and "Save to the library" (AJAX `fw_forms_library_save`, nonce `fw_forms_library`) saves an element's form.
- **Richer fields and steps (since 2.0.71):** field types `name` (options `format` full|first_last, `first_label`, `last_label`; posts `name[first]/[last]`), `phone` (type tel; `placeholder`), `address` (`show_line2`, `show_region`, `default_country`; posts `[street|line2|city|region|postcode|country]`, required = street+city+country), `section` (`label` heading, `text`, `level` h3|h4|h5; no value), `page-break` (`label` = next step title, `next_label`, `back_label`; splits the form into steps — `static/js/steps.js`), `range` (`min`, `max`, `step`, `default`, `prefix`, `suffix`), `image-choice` (`choices` addable-box `{caption, image}`, `multiple`, `columns` 2|3|4), `ranking` (`choices` strings; posts `{text: position}`), `likert` (`rows`, `scale` strings; posts `{row: point}`). Values are stored as one readable string each. Front-end scripts: `fw-ext-forms-steps`, `fw-ext-forms-fields`; events `fw-forms:errors`, `fw-forms:sent` on the form.
- **Entry hooks:** `fw_ext_forms_store_entries` (bool), `fw_ext_forms_entry_before_insert` (filter the entry; return `array()` to skip), `fw_ext_forms_entry_stored( $id, $entry, $payload )`, `fw_ext_forms_entry_form_title` (a form type supplies a human title — the contact form answers with its subject), `fw_ext_forms_entries_capability`.

- **Pre-fill, piping, floating labels, one question at a time, repeater (since 2.0.72):** `FW_Forms_Prefill::values( $items )` (logged-in user → CRM contact → `$_GET[<shortcode>]` → filter `fw_ext_forms_prefill_values`; never over posted values); `{shortcode}` answer piping in labels / legends / section / help text (`fields.js`, text only); Form Styles `label_position: floating` + preset `formp-floating-labels`; contact form `form_layout: conversational` (`static/js/conversational.js`, before `steps.js`); field type `repeater` (`fields` addable-box `{label, type, required}`, `item_title`, `min`, `max`, `add_label`).

- **Notification switch (since 2.0.73):** contact form `email_notify` (`'no'` = store + run actions, send nothing). A plugin can add a form field and an action together for a reservation flow: the field keeps its parsed value in a static during `frontend_validate()` (actions only get each field's readable text), pre-allocates any reference it wants answer tags to show (the success message is built BEFORE actions run), and adds tags through `fw_ext_forms_merge_tags`.

- **Prices, totals and payments (since 2.0.74):** fields `product`, `amount`, `calculation`; `FW_Forms_Order::build( $items, $posted )` → `{ lines, total, currency }` (filter `fw_ext_forms_order`), `FW_Forms_Formula::evaluate( $formula, $ref )`, `FW_Forms_Money::format() / currency()` (Forms Settings → Payments → `payments_currency`, filter `fw_ext_forms_currency`). ## AI ability: `forms-add` actions (2.0.64)

`forms-add` places a contact form from a starter and / or fields, and also sets the form's **actions**: `store` (default true; keep every submission under Form Entries), `subscribe { list, tags?, name_field? }` (writes `action_subscribe`, `action_subscribe_list`, `action_subscribe_tags`, `action_subscribe_name`; the list must exist, so create it with `crm-save-lists` first; add a consent field with purpose newsletter, because only people who tick it are subscribed), `crm { add_contact, create?: deal|task|case, pipeline? (name or id), task_type?, tags? }` (since Forms 2.0.90: the CRM's "Add to the CRM" action, `action_crm_contact` / `action_crm_create` / `action_crm_pipeline` / `action_crm_task_type`; every sender becomes a contact, never a subscriber, so no consent field is needed for it), and `failure_message`. The `subject` may use Dynamic Content tokens. There is still no ability that reads entries.

## Notes / gotchas

- **Front-end submissions are rate-limited** (since 2.0.57): `_frontend_form_validate()` refuses the 11th submission in 10 minutes from one visitor (`fw_rate_limit_exceeded( 'fw_ext_forms_submit', 10, 600 )`, error key `rate-limit`; `edit_posts` users exempt; tune or disable with the `fw_rate_limit` filter). A nonce and the honeypot do not bound volume, and each submission can send mail.
- **Sends mail through the `mailer` extension** — that's how global email/SMTP options apply to form submissions. With no send method chosen the Mailer uses **WordPress mail** (`wpmail`), so a new site's forms send out of the box; configure SMTP on a live host (see `mailer.md`).
- **A failed notification email no longer looks like a failed submission.** When the email fails but the submission is being stored as an entry (global entries switch on + the form's Store entry action on), the visitor sees the **success** message and the entry gets an extra field *Notification email: "Not sent. <mailer error>"* (action `fw:ext:contact-forms:mail-failed` fires). Only when nothing is stored does the visitor see the failure message.
- **File Upload fields are stored privately** in `uploads/unysonplus/form-uploads/` — deny rules (`.htaccess` / `web.config`) plus random file-name prefixes keep them off the web; admins download them from the entry screen (Unyson+ → Form Entries). Deleting an entry deletes its files. They are also attached to the notification email.
- **Requires the `builder` extension** (the form-builder option type is built on the base builder); the Contact Forms sub-extension requires `mailer`. Neither is in the core-only plugin zip — the Extensions manager pulls them in with Forms.
- Standalone, displayed extension; the contact-form is both a shortcode and a native page-builder element.
- **The submit hook is the one seam.** `fw_ext_forms_frontend_submit` now carries `form_values` (shortcode → value) and `attachments`; before 2.0.50 a listener could see that a form was submitted but not what. Entries, and later the CRM's subscribe action and webhooks, all listen here — nothing is threaded into the pipeline itself.
- **An entry stores `{ id, type, label, value }` per field with the label captured at submit time**, so editing a form never makes old entries unreadable. Fields are JSON; `email`, `form_id`, `status`, `created_at` are real indexed columns.
- **An entry is written whether or not the email sent** — that is the point of storing them.
- **Entries are submissions, not people.** A submission never creates a CRM subscriber by itself; that needs an explicit consent field and the CRM's own subscribe action through double opt-in (Forms plan, Phase 3).
- `wp_get_referer()` returns `false` when the referer is the current page — which a form posting to its own page always is — so the entry's `post_id` is resolved from the raw referer / request URI instead.
- CSV export prefixes cells beginning with `= + - @` with `'` (spreadsheet formula injection); the export streams in chunks and never loads the table into memory.

## Refusing a submission, and secret fields (2.0.66)

- `fw_ext_forms_validate_submission( $errors, { id, type, shortcode_to_item, form_values } )` runs in
  `_frontend_form_validate()` once every field is valid. Add `key => message` to refuse: the visitor sees the
  message and nothing is sent, stored or run. `FW_Forms_Actions` uses it to call each enabled action's optional
  `FW_Forms_Action::validate( $ctx )` (return a message string, or null) — for checks the visitor can act on,
  such as "that email already has an account" (Membership's Register member action).
- `fw_ext_forms_secret_field_types` (string[]): field types whose value is a secret (Membership adds
  `member-password`). They are skipped by `FW_Forms_Entries_Capture::fields_from_submission()` (so never stored
  in Entries and never in an action's `fields`) and by the contact form's notification email. An action that needs
  the value reads it from the raw `payload['form_values']`.
- `FW_Forms_Actions::context( $data, $form )` builds the context both `validate()` and `run()` receive.
