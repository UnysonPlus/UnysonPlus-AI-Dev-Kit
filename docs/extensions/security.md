# security extension

Login throttling, two-factor sign-in, XML-RPC and header hardening, anonymous user-listing limits, an emergency session reset, a custom login address, and security checks added to core's Site Health screen. Its premise: ship only measures that stop a named attack or tell the owner the truth about configuration the plugin cannot enforce — and say, in each option's own description, what the measure does **not** protect against. **Active by default:** no — deliberately **not** seeded by `fw_upw_seed_default_extensions()`; it changes how people sign in, so it must be a deliberate choice. After activation only the read-only checks run; every behaviour-changing measure is its own switch, off. Version: 1.0.4. Repo: `UnysonPlus-Security-Extension` (branch `main`). Requires PHP 8.0.

## Provides

- **Settings page:** Unyson+ → **Security** (`admin.php?page=fw-security`, `manage_options`) — native nav-tabs: **Status** (measures on/off, lockout list with Unlock, Tools), **Login**, **Two-factor**, **Hardening**, **Login address**. The Extensions manager's generic Settings link redirects here (see *Own admin page* below).
- **Settings** (stored raw in the `fw_ext_settings_options:security` option; defaults in `FW_Extension_Security::defaults()`):

| Key | Default | Meaning |
|---|---|---|
| `throttle_enabled` | `false` | Login throttling (wp-login.php, XML-RPC logins, REST application-password auth) |
| `throttle_attempts` / `throttle_window` | `'5'` / `'15'` (min) | Failures per address + username before a cooldown; one address trying many usernames cools down after 4× this |
| `throttle_lockout` / `throttle_lockout_max` | `'15'` (min) / `'12'` (h) | First cooldown; doubles per repeat within a day, capped. Never permanent |
| `throttle_allowlist` | `''` | Addresses / CIDR ranges never throttled, one per line |
| `proxy_header` / `proxy_header_custom` / `proxy_trusted` | `'none'` / `''` / `''` | Where the real visitor address comes from behind a proxy/CDN, and which proxies to believe (empty = private-network proxies only). When set, also feeds the framework's shared rate limiter through `fw_rate_limit_client_ip` |
| `generic_login_errors` | `false` | One message for wrong username or wrong password |
| `twofa_enabled` | `false` | Offer TOTP two-factor sign-in (each user opts in on their profile) |
| `xmlrpc_mode` | `'leave'` | `leave` / `pingbacks` (remove pingback methods, `X-Pingback`, pingback link) / `block` (403 before the server loads) |
| `hdr_frame`, `hdr_nosniff` | `false` | Front-end `X-Frame-Options: SAMEORIGIN` + `frame-ancestors 'self'`; `X-Content-Type-Options: nosniff` |
| `hdr_referrer` | `'off'` | `off` or a `Referrer-Policy` value |
| `hdr_hsts` / `hsts_max_age` / `hsts_subdomains` | `false` / `'86400'` / `false` | HSTS, HTTPS only; switching it off sends `max-age=0` for the old duration (wind-down) |
| `limit_user_listing` | `false` | Logged-out only: `?author=N` → 404, `/wp/v2/users*` → 401, no author in oEmbed |
| `login_slug` | `''` | Custom login address; `''` = standard wp-login.php. Single-site only; needs non-plain permalinks |

- **wp-config.php constants:** `UPW_SECURITY_SAFE_MODE` (every behaviour-changing measure off; checks still run; red admin banner), `UPW_SECURITY_LOGIN_SLUG` (string overrides the slug; `false`/`''` forces stock wp-login.php), `UPW_SECURITY_2FA_KEY` (optional, ≥16 chars: encrypts TOTP secrets with AES-256-GCM; without it they are stored unencrypted and the Two-factor tab says so).
- **WP-CLI:** `wp upw-security status | disable <throttle|errors|2fa|xmlrpc|headers|user-listing|login-url>|--all | unlock --ip=<ip>|--all | logout-all | purge`, `wp upw-security login-url get|reset|set <slug>` (`set` runs the save-time validation), `wp upw-security 2fa reset <user> | list`. All work in safe mode.
- **Site Health tests** (`site_status_tests`, badge "Security"): direct — file-editor constants, salts, XML-RPC state, application passwords issued, proxy/visitor addresses, safe mode, administrators without 2FA, login-slug collisions, SVG upload roles (via `sc_svg_upload_roles()`); async (loopback; answered on `wp_ajax_health-check-upw_security_<id>`) — public debug log, uploads directory listing, security headers actually returned. A loopback failure reports "could not check", never a pass. The PHP-in-uploads probe is **on demand only** (Status → Tools): it writes, requests and deletes a random-named file.
- **Profile screen** (when 2FA is on): enrol (QR drawn in the browser from the `otpauth://` URI — the secret never goes to another service), 10 single-use recovery codes (stored as password hashes), new codes / turn off (both need a current code), and for an admin editing someone else: **Reset two-factor sign-in**. AJAX actions `upw_sec_2fa_{start,confirm,disable,codes,reset}`, nonce `upw_sec_2fa_<user_id>`.
- **Status tools:** Log everyone out (`WP_Session_Tokens::destroy_all_for_all_users()`), Check whether PHP runs in uploads, Remove all security data — via `admin-post.php?action=upw_security_action&op=…` (nonce `fw_ext_security_action`), destructive ones behind `fw.confirm()`.
- **Data stored:** the settings option; lockouts in `upw_security_lockouts` (≤200 entries: hashed address, masked label like `203.0.113.x`, attempted username, expiry — never a raw IP); counters/locks as `upw_sec_*` transients keyed by an HMAC of the address; `upw_security_hsts_winddown`; user meta `upw_sec_2fa`, `upw_sec_2fa_pending`, `upw_sec_2fa_recovery`, `upw_security_intro_dismissed`. **Remove all security data** / `purge` deletes all of it.

## How it is built

| File | Job |
|---|---|
| `class-fw-extension-security.php` | Settings reader, safe mode, module boot, own admin page + save/validation, post-save guard, notices |
| `lib/class-fw-security-ip.php` | Client address (trusted-proxy aware), CIDR matching, hashing, masking |
| `lib/class-fw-security-throttle.php` | Throttling + `FW_Security_Login_Errors` |
| `lib/class-fw-security-totp.php` | RFC 6238 / base32 — pure functions |
| `lib/class-fw-security-two-factor.php` | Enrolment, login step (`wp-login.php?action=upw_2fa`), recovery codes |
| `lib/class-fw-security-hardening.php` | XML-RPC, headers, user listing, sessions |
| `lib/class-fw-security-slug-rules.php` / `…-login-url.php` | Slug validation; the stateless login address |
| `lib/class-fw-security-site-health.php` / `…-cli.php` | Checks; WP-CLI |
| `tests/security-contracts-test.php` | `wp eval-file` it: TOTP vs the RFC 4226/6238 vectors, base32, CIDR, cooldown maths, slug format, URL rewriting. Exit 0/1 |

**Every module registers its hooks only when its switch is on and safe mode is off.** Off = no hooks, so an off measure is indistinguishable from stock WordPress (verified: all responses identical with the extension inactive vs. active-with-everything-off). Nothing is persisted outside the options/transients/meta above — no rewrite rules, no files, no `wp-config.php` / `.htaccess` edits — so deactivating the extension or the plugin (or a fatal) returns WordPress to stock at once.

## Notes / gotchas

- **Classes live in `lib/`, not `includes/`.** The extension loader plain-`include`s every file in an active extension's `includes/` folder; with the main class also `require_once`-ing them, activation fataled with "Cannot declare class". Loading explicitly from `lib/` also keeps the WP-CLI file out of web requests.
- **Settings are read raw in `_init()`** (`get_option( 'fw_ext_settings_options:security' )` merged over `defaults()`). `fw_get_db_ext_settings_option()` loads `settings-options.php` to fill defaults, which initialises the option types; doing that from `_init()` — before other extensions register theirs — left the page-builder type undefined and every page with builder content 500'd.
- **Own admin page, because the manager's generic Settings form cannot validate per extension** — `FW_Extensions_Manager::_extension_settings_form_validate()` checks capability only and the extension hears about a save afterwards (`fw_extension_settings_form_saved:<name>`). The page saves on its `load-` hook; invalid fields keep their previous value and every reason is shown ("The login address was NOT changed — …"). The generic screen redirects to the page, and `_after_manager_settings_saved()` re-validates anything that arrives through it anyway.
- **Application-password auth has two paths.** XML-RPC (and wp-login.php) run it inside the `authenticate` filter; REST Basic auth calls `wp_authenticate_application_password()` directly and only fires `application_password_failed_authentication`. Core's "application passwords in use" flag stays set once any has existed, so on XML-RPC that action fires too. Throttling counts it only when not `doing_filter( 'authenticate' )`; otherwise it would count with an empty username and miss the lock. Locked correct app passwords are refused through `wp_authenticate_application_password_errors`.
- **A lock refuses a correct password too** (`authenticate` at 999, after core's check) — letting it through would tell an attacker when a guess was right. An address-wide lock (many usernames from one address) locks every account from that address, including the admin's; `wp upw-security unlock --all` or the safe-mode constant lifts it.
- **The 2FA step:** `authenticate` at 1000 swaps an enrolled user's `WP_User` for a redirect to `wp-login.php?action=upw_2fa&upw_2fa_token=…` (5-minute transient; ≤5 tries), rendered with core's `login_header()`/`login_footer()` so the Admin Skin styles it. A used TOTP step is remembered (no replay, including the step used to confirm enrolment). XML-RPC password logins are refused for enrolled users; REST/AJAX/CLI get an explanatory error; application passwords pass by design. Interim login (`interim-login=1`) is carried through and ends on `interim-login-success`.
- **The login address is stateless.** At `wp_loaded` priority 1: a request whose path equals the slug declares the globals wp-login.php's functions read (`$error`, `$interim_login`, `$action`, `$user_login`), sets `$pagenow`, sets `$_SERVER['SCRIPT_NAME']` to the slug path (core's `is_login()` compares it with `wp_login_url()`), and `require`s wp-login.php. Direct wp-login.php → theme 404 (except `action=postpass`, which is not a login); logged-out `/wp-admin/` → 404 so the redirect cannot reveal the slug (admin-ajax / admin-post untouched). `site_url`, `network_site_url`, `wp_redirect` (including core's relative `wp-login.php?checkemail=confirm`), `lostpassword_redirect`, `registration_redirect` are rewritten. `FW_Security_Login_Url::stock_url()` builds the unfiltered address for messages in the same request that resets the slug.
- **Slug validation** (`FW_Security_Slug_Rules::errors()`): format (4–50 of `a-z0-9-`), a reserved list (WordPress paths plus `login`/`admin`/…, the first guesses), multisite and plain-permalink refusal, public query vars, post-type/taxonomy rewrite bases, any post with that slug (any status, incl. trash), and the decisive check — the first matching rewrite rule's query resolved as `WP::parse_request()` would; then a file/folder of that name. After saving, a loopback request must show `id="loginform"` at the new address or the previous slug is put back. The URL is emailed to the admin address.
- **Deactivation with a slug set restores wp-login.php immediately** — tested with the extension deactivated, the whole plugin deactivated, `UPW_SECURITY_LOGIN_SLUG` false, and safe mode.
- **Headers are front-end only** (core already sends frame + referrer headers on login/admin) and appended, not replaced (the page builder appends `Permissions-Policy` on editor screens). PHP-sent headers never reach static files or page-cached HTML — the Site Health check reports what visitors actually get. HSTS refuses to switch on unless the site address is HTTPS.
- **Proxy guard:** saving throttling as on is refused while `REMOTE_ADDR` is private/loopback and a forwarding header is present with no `proxy_header` configured — every visitor would share one address.
- **Theme Settings interplay:** Misc → Performance `perf_disable_xmlrpc` ("Disable XML-RPC logins") only sets `xmlrpc_enabled` (authenticated methods off; pingbacks still answer). Its description says so, and switches to "the Security extension is handling XML-RPC" while `xmlrpc_mode` is not `leave`.
- **Assets** go through `fw_min_uri()`; the build (`unysonplus/build`, `npm run build`) lists them in `framework/build-manifest.php`. The bundled QR generator (`static/js/vendor/qrcode.js`, MIT) ships with its licence file; it loads on the profile screen only.
- **Testing in a headless browser:** WordPress 7's wp-admin `@view-transition` (inside `prefers-reduced-motion: no-preference`) stalls headless rendering after a POST-redirect; run the browser context with `reducedMotion: 'reduce'`.
- **Deliberately not built** (reasons in the Design Decisions log, "security-extension-scope"): PHP request firewall, malware scanner, version hiding as security, table-prefix changes, writing wp-config.php/.htaccess, blocking REST for anonymous visitors, an enforcing auto-generated CSP, permanent or per-username lockouts. Waiting: an auth event log, 2FA enforcement by role, breached-password checks, core file integrity, CSP report-only.
